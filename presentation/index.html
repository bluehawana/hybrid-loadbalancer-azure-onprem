Honest diagnosis

A load balancer only helps if it lives
outside the thing it protects.

01

Same failure domain

An on-prem LB sits on the very boxes it guards. The host dies, the balancer dies with it.

02

Correlated hosts

Two servers, same age, same room, same load. Balancing between two failing boxes adds nothing.

03

One server room

One power, cooling or network failure takes the servers, the LB and the door — all at once.

HYBRID FAILOVER09
Under the hood · for the team

A clock. A probe. One command.

// 1 · THE CLOCK — Worker.cs — wake every few seconds, check, sleep again
while (await timer.WaitForNextTickAsync()) Evaluate(each service);

// 2 · HOW WE DETECT — ask the SERVICE, not the box
var probe = Check(service /health);  // 200=alive · 503/timeout/refused=down
var dead      = probe failed N times in a row; // independent of CPU/RAM
var overloaded = cpu || mem || latency over limit; // early warning only

// 3 · THE ANSWER — one runtime command drains on-prem → Azure serves
switch (state) { Healthy: if (dead) FailOver(); … }
haproxy ← "set server be_webapp/onprem state drain"
WHY A CLOCK

A timer checks, then sleeps — steady and predictable, no CPU burn, nothing missed.

HOW WE DETECT

We call the service's own health, not the host. Box up but service dead → probe fails → we act.

THE ANSWER

One command drains on-prem; HAProxy's warm backup serves from Azure in ~6s. No reload.
