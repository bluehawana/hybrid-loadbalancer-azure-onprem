The 2:30 AM problem

Today, recovery depends on a human waking up

What happens now

An on-prem host (e.g. ONPREM-WEB-01, web app host) overloads or dies. Splunk pages the on-call. Someone wakes up and manually runs the release pipeline to restart it.

The cost

hours

of downtime per incident — customers notice, and the uptime target slips out of reach.

Root cause

The services still live on aging physical servers with no automatic fallback. Single point of failure, no safety net.

We borrow the proven idea from cloud load balancers — health-based failover — and adapt it to our hybrid on-prem + ARO world.

Honest diagnosis

Why today's load balancer doesn't save us

① Same failure domain

Our LB sits on the same on-prem servers it is meant to protect. When the box goes, the balancer goes with it. Who watches the watcher?

② Correlated hosts

ONPREM-WEB-02 and ONPREM-WEB-01 are the same age, same room, same load. When one is overloaded, so is the other — balancing between two failing boxes adds nothing.

③ Hard to run

A self-managed on-prem load balancer needs constant expert tuning. That's not where the team's strength is — so it doesn't behave as expected.

A load balancer only helps if it lives outside the thing it protects.

The real risk

Even a perfect on-prem LB dies with the server room

The whole on-prem site is one failure domain. One incident takes down the servers, the LB, and the entry point together — and clients can't even reach the site:

  • 🌐 Internet / network link to the site drops
  • 🔥 Cooling / heating fails, hardware overheats and shuts down
  • ⚡ Electricity outage in the server room

If any of these hit, an on-prem-only balancer is powerless — there is nothing left, on that site, to fail over to.

On-prem server room

The solution · hybrid, two datacenters

Decision in Azure. On-prem + Azure. Never the same room.

  • The failover decision runs in Azure (ARO) — a different datacenter, so a server-room disaster can't take it down.
  • On-prem (ONPREM-WEB-02/62) = primary. Azure = standby. Two independent failure domains, like cloud availability zones.
  • Health-based failover shifts traffic to Azure before a host dies, on overload, on death — or on a full site outage.
  • It also auto-triggers the restart pipeline to repair on-prem — no 2:30am human.
  • Every failover + Azure minute recorded for a cost comparison.

Three triggers to shift

Dying soon sustained high CPU / memory / latency → shift early

Overloaded SLO breach → shift

Dead / site down health checks fail → immediate shift

Recovery: on-prem healthy for a stable window → drain back to the cheap datacenter.

Clearing up a common question

The Azure VM runs the real service — it is not a proxy

HAProxy is the only proxy (it runs in ARO). It never does the work — it just steers each request to whichever copy is healthy.

The Azure VM is a warm standby running the same web app — same HTTPS :443, same /health/ready — so on failover it genuinely serves traffic.

Receptionist (HAProxy) routes the call. Office A = on-prem. Office B = the Azure VM, which must be a real, equipped copy — not a second receptionist. Forwarding to a dead on-prem would be pointless.

It works if two things hold:

  • The app can run on the VM (installed or containerized), listening on :443 with a health endpoint.
  • It can reach its data + dependencies from Azure (database, file shares, licenses, other services).

The one question that decides the effort

Easy Web app is stateless + reads a shared DB reachable from Azure → just install the app on the VM and point it at the same DB. True hot copy.

Harder Web app depends on on-prem-only things (local shares, other on-prem services, hardware/licenses) → those must be reachable from Azure, or data replicated. That's its own project.

Our load balancer decides *when* to fail over; provisioning + syncing the standby is the piece to confirm.

Beyond Web app

A reusable template for the whole team

Most services still run on the same old on-prem boxes. Onboarding one is 4 steps:

  • Add an HAProxy backend (on-prem primary + Azure backup).
  • Add a service block in services.yaml (health + thresholds).
  • Add a Route for the hostname.
  • Import the Grafana dashboard + alert rule.

Test on ARO test/qa first — never prod until we agree.
